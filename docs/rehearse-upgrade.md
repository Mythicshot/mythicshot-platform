# Rehearse an update on a copy of your data

`npm run rehearse:upgrade` tries an update on a copy of a site's data, on your own computer, before the real update runs. The steps for a cPanel backup are in [the cPanel guide](hosting/cpanel.md#rehearse-an-update-on-a-copy-of-a-backup); this page is the reference for the command.

> [!WARNING]
> The data folder holds real data: the owner's email, the token hashes and every image, and a backup folder also holds the settings file with the setup code and any mailbox password. Keep the copy as private as the backup itself and delete it when you are done. The command copies only `db.sqlite`, `drafts` and `public` into a scratch folder, removes that folder at the end, and never reads the settings file.

## The command

```sh
npm run rehearse:upgrade -- <data folder> <old build> <new build>
```

The data folder is a data folder or a backup folder made by `cpanel.sh backup`. It is never written to and never opened by the database: its files are hashed at the start and again at the end, and the report says whether they are unchanged.

Each build is a folder with `dist/node/entry.js`, `migrations` and `package.json`, and its packages installed: an unpacked archive after `npm ci --omit=dev --ignore-scripts`, or a checkout after `npm run build`.

## Settings

| Setting | What it does |
|---|---|
| `REHEARSE_TOKENS` | The tokens whose view of the site is compared, separated by spaces, commas or line ends. At least one is needed. They are never printed or written anywhere |
| `--tokens-file <file>` | Instead of `REHEARSE_TOKENS`: a file with one token per line |
| `REHEARSE_MODE` | `one` (the default), `two` or `three`. With `two`, both builds run with the two addresses `tours.example.com` and `app.example.com`. With `three`, they also get the address for images and clips, `img.example.com` (`IMG_HOST`), as described below. `--mode one`, `--mode two` or `--mode three` does the same |

With `three`, the old build gets the third address only when it knows that address, which came in 0.1.19. The command reads this from the build's own compiled files and does not start the build to find out: the build's list of address roles (`dist/hosts.js`) must name `img`, and its settings (`dist/node/config.js`) must read `IMG_HOST`. An old build that does not know it runs with the two addresses and the new build with three, and the report says so in one line under its first line. A new build that does not know the third address cannot be rehearsed with `three`; the command stops and says to use `two`. Each build is checked for health on every address it has, the third one included, and with two or three addresses its health answer there must name that address's own role (`tours`, `app` or `img`), so a build that was given `IMG_HOST` but does not take it fails to start with a line saying so, never passing as three addresses while it runs with two. With one address the health answer is taken as before. The per-address checks of step 1 below run unchanged on the tours and app addresses, so a build with three addresses is compared with one with two answer by answer.

Nothing else of your environment reaches the builds: no mail settings and no setup code. Each build runs on `127.0.0.1` only, on a free port, and no request goes anywhere else.

Every build, old and new, in every mode and every step, runs with `CLIENT_ADDRESS_HEADER=X-Forwarded-For`, and every request the command sends carries `X-Forwarded-For: 203.0.113.7`, an address set aside for documentation. A real site runs behind a proxy that writes the visitor's address into such a header, and the command stands in for that proxy, so each build sees a known visitor address as it does on the site. Without it, a build from 0.1.26 on would see every request come from `127.0.0.1` and write its one line asking for the setting, which the check of the two new builds would count as an error. Builds older than the setting, such as 0.1.7 and 0.1.8, read neither the setting nor the header, so both change nothing for them.

## What it checks

1. The old build on the copy: the health of each address, then for each token the workspace, the tour list and the usage (when the build has it), every listed tour's page and every picture on it, and every shared image or clip of the token's workspace (below).
2. The new build on the same copy, which applies the pending database changes as it starts. Every answer must be the same to the byte, except the `date` header, the version number in the workspace answer, a JSON answer that only adds fields (below), a tour's page that names the new build's player files (below), a shared item's cache rule (below), and a page's policy that gained `font-src 'self'` (below). A route the old build did not have, the usage, is checked against a sum the command makes from the database itself.
3. Every file of both image stores, every row the old tables had in the columns they had, the new account tables with one membership and one sign-in method per account and no admin, the database's own two checks, and the list of applied changes.
4. The way back: the old build again, on the changed copy, must answer as it did before the update. Here no added field and no other player file name is allowed: every answer must be the same to the byte but the `date` header.
5. Two new builds started at the same moment on a fresh copy (with the items the command shared, when it shared any, below): both start, write nothing to their error output, each database change is applied once, and every answer is the same to the byte as the single new build's but the `date` header, with no answer set aside as new. When either writes an error line, the report names each distinct line once: one of the app's own fixed messages word for word, and any other line only as "an error line that is not one of the known messages" with its length, because it could hold data.

A JSON answer only adds fields when its new body is the old body with new keys in its objects, at any depth: every old key is still there, in the same order, with the same value, and every list has the same length, its items compared one by one under the same rule. Both bodies must also be written exactly as plain JSON writes their values, so a number written another way (`1.0`, `-0`, an integer too large to keep exactly), a repeated key, a byte order mark or a space fails. Every added key must be shaped like a field name: lowercase words joined by underscores, at most 40 characters, with no digit and no capital. An added key of any other shape, such as an item id, a token or a link id, fails the answer, and the report says only that it added a key not shaped like a field name, never the key. Such an answer is allowed in step 2 and counted on its own ("differ only by added fields"), and the report names each added field once per route by its path, such as `images` or `tours[].views`, never with a value. Its `content-length` header may differ; no other header may. A changed or removed value, a value of another type, a list of another length or another status still fails, and an answer that is not JSON must still be the same to the byte.

A tour's page (`/t/<slug>`, an HTML answer) names the player's script and stylesheet by names that hold a hash of their content, such as `/player.<16 hex digits>.js`, so every release that changes the player changes those names in every page. In step 2 only, a page may differ in them: in both pages, the name inside the page's own `<script src="…" defer>` and `<link rel="stylesheet" href="…">` tags, written exactly as the server writes them, is replaced with one fixed stand-in before the bytes are compared. Both pages must then be the same length and the same in every other byte, and each may name each file once at most. Its `etag` header may then differ, since it is a hash of the page, but on each side it must be exactly that page's own, by the server's rule (the first 32 hex digits of the page's SHA-256, in double quotes), so a stale or fixed `etag` for a changed page fails; it may not differ when the pages are otherwise the same to the byte, and no other header may differ. Such a page is counted on its own ("differ only in the player's file names"), and the report never shows the names. A tour's own title and texts are written into the page escaped, so they can never make one of those tags: a title or step that holds text shaped like a player file name is compared byte for byte like the rest of the page, and fails when it changed. A changed picture address, title, step text or status still fails. After the comparison, every player file the new build's tour pages name is asked of the new build itself, on the tours address, and must answer `200` with the script's or the stylesheet's content type; the report gives one line with the counts, and names no file.

The shared items asked are the published ones (online, public or restricted) of each token's workspace that the data holds before the update, read from the database copy, never from a build. For each, on the media address (`img.example.com` with three addresses, otherwise the tours address), the command asks its page `/i/<link>` or `/r/<link>`, its file with its one extension, `/download` and `/preview`, each with GET, with HEAD and, when the GET answer carried an `ETag`, with that `ETag` in `If-None-Match`, and its file once more with `Range: bytes=1-100`. With two or three addresses its page is asked on the app address as well. The links are kept in memory and never printed. Every one of these answers is compared under the same rules as the rest.

Before anything is recorded, the old build is started on the copy and each of those items' files is asked once. If at least one answers with the file, the report says how many items there are and how many serve their file, and they are used as they are; an item left out because its type is not one the item routes serve, or its link is malformed, is counted in that line. If none does (the data holds no item, or every item is restricted or answers as one that does not exist), the report says so in its own line, and the old build, still before anything is recorded, shares one public image (an 8 by 8 PNG of 1,200 bytes, "Rehearsal image") and one clip (an 8 by 8 GIF of 900 bytes, "Rehearsal clip"), each with a 4 by 4 preview, for the first token through its own API (`POST /api/v1/media`), and both must serve their file; the report line says it did. So the old build, the new build, the way back and the two new builds all run on the same data with those two items in it, and the rows and stores checks hold as before. The share route is read from the old build's compiled files (`dist/media.js`); it is in builds from 0.1.19 on, in the shape the command sends from 0.1.24. An old build without the route and one whose API refuses the share (the report names the statuses) each give a line that starts with SKIP and says why; the data's own items, if any, are still asked. Whether the old build has pages for shared items is read from its `dist/app.js` (a call of `sharePageRoutes`) and from its version (0.1.20 and later have them); when the two disagree, a FAIL line says so and the build is taken as having pages. A version that cannot be read never counts as having no pages: when the compiled files also show none, a FAIL line says the detection cannot be trusted alone, and the build is taken as having pages, so its items are compared. Even when both say it has none, its items' files are asked: if any answers with the file, a FAIL line says the detection is wrong and the items are compared; only when none does is it a SKIP. A wrong reading of the compiled files can so only make the command stricter. After the old build is recorded, a line counts its item answers by status and how many of its file answers served the file; when none did, a SKIP line says that no served item file is compared.

From the old build to the new one only, and only when the old build is from before 0.1.47 by both its compiled files (it does not know who may view an item: no `dist/media-access.js` with the access route) and its version number (an unreadable version allows nothing; when the two disagree, a FAIL line says so and nothing is allowed), a shared item's answer (page, file, download or preview, with GET or HEAD, so a `304` and a `206` too) may differ in its `cache-control` header alone, from exactly `public, max-age=60` or `public, max-age=3600` (what 0.1.46 and earlier send) to exactly `no-cache` (what 0.1.47 and later send), with every other header, the status and every byte the same. A line under the answers then checks that each item answer that carried the old rule differs only in it. When the old build is from 0.1.47 on, nothing is allowed, and the line is a check that fails if any of its item answers carries the old rule. On the way back no such difference is allowed.

From the old build to the new one only, an HTML answer (a tour's page, a shared item's page, a gate or a not-found page, by its content type) may differ in its `content-security-policy` header alone, when the new policy is exactly the old one with `font-src 'self'; ` written right after `style-src 'self'; ` and the old one has no `font-src` at all. 0.1.54 serves the brand's fonts from the site itself, so each page's policy gained that one directive and nothing else. Only the header is swapped before the answers are compared: the status, every other header and every byte must still be the same, or meet one of the other allowances as they are (a tour's page then also differs in the player's file names). Such answers are counted on their own ("pages' policies gained only font-src 'self'"). On the way back no such difference is allowed.

The restriction step (the way back with a restricted tour) runs the new build with placeholder mail settings: a mail server on `127.0.0.1` port 9 with the user `rehearsal` and the password `not-a-real-password`, none of them real. Restricting a tour needs a site that can mail, but nothing is mailed by it and no connection is made. When the new build refuses the change, the report names the refusal's error code, such as `cannot_restrict`, and nothing else of the answer.

What the old build must then answer depends on whether it can serve restricted tours, which came in 0.1.44. The command reads this from the build's own compiled files and does not start the build to find out, nor look at the data or the version number: its app (`dist/app.js`) must import `restrictedAnswer` from `./restricted.js` and hand it to the page routes, and `dist/restricted.js` must have the route `/t/:slug/v/:name`.

- An old build that cannot serve them knows nothing of the setting: the tour's page and every picture its public page named must answer exactly as for a tour that does not exist.
- An old build that can serve them answers the tour's page, to a visitor who proved no address, with its gate. That answer must be a `403` whose `cache-control` says `no-store`, which no cache may keep, with no `etag`, that forbids framing (`X-Frame-Options: DENY` or `frame-ancestors 'none'`), and whose body holds nothing of the tour: not its title, no text of its data of 4 characters or more (the cover, the call to action, the end card, chapter titles and descriptions, and each step's id, caption, notes and card), no picture address or name, and not its id, each looked for as written and HTML-escaped. That content comes from the tour's public page as the new build served it before the restriction; it is kept in memory and never printed. Every picture address from that page, and `/t/<slug>/v/<name>` for each picture name, must answer exactly as an unknown picture does on the same route, and never with picture bytes.

Either way the report gives one line with labels and counts, and a failure says only which kind of content it found, never the content.

Then the way back with a restricted item, on another fresh copy: the new build restricts one online shared item of the first token's workspace to `me` through its own API, with the same placeholder mail settings. When the workspace has no item, the new build first shares a small image (an 8 by 8 PNG of 1,200 bytes, title "Rehearsal") through the same API, on the copy only, and the report says so in its own line. Before the restriction the new build must serve the item's file; after it, the new build must answer its gate for that file without the file's bytes. Then the old build is started on the copy. What it must answer depends on whether it knows who may view an item, which came in 0.1.47, read from its compiled files (`dist/media-access.js` with the route `PUT /api/v1/media/:id/access`):

- An old build that does not know it: the item's page, file, download and preview must each answer exactly as the same address of an item that does not exist (status and body), and no answer may hold the file's bytes. Migration 0016 keeps a restricted item's link out of the column such a build looks items up by.
- An old build that knows it: each of the four must answer `403` with `no-store`, no `etag`, and none of the file's bytes.

The item's link and bytes are kept in memory only; the report gives labels and counts.

The report is one line per check, PASS or FAIL with counts, and ends with `RESULT: PASS`, `RESULT: PASS, with N added fields to read above` or `RESULT: FAIL`. It never holds a token, an email address or a name from the data. The command exits with status 1 when a check fails, and with 0 for both kinds of pass.

> [!WARNING]
> When the last line says `with N added fields to read above`, read the `added fields` lines under the answers check before you update. Each names a field the new version adds to an answer. An added field is usually a new feature, but it can also be data that should not be there, such as something of another workspace, and only a person can tell the two apart.

## What it does not prove

It does not test the hosting: not how the hosting starts the app, not its file system and not its version of Node.js. It proves only what the given data holds; a kind of tour the site does not have is not tried.

## Synthetic data

`node scripts/rehearse-fixture.ts <empty folder>` builds 0.1.7, 0.1.8 and this checkout from Git without the network, runs each released build on a new data folder, and writes a site through its own routes: the setup wizard, tours with several chapters and a logo, published, unpublished, renamed, replaced and deleted, and an unfinished upload. It prints the command to run next.
